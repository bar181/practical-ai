What is an AI harness?

A practical introduction to how harnesses help teams turn AI agents into reliable, repeatable, company-aligned work.

A model can generate code, text, and plans. An agent adds tools and can take action. A harness is the system around that agent.

The harness controls things like what the agent can access, what rules apply, how work is checked, and when the task is complete.

Why care? Because the same model can produce very different results depending on the harness around it. Better harnesses make agent work easier to trust, repeat, and improve.

Starter

Do not start with a long prompt. Start with a clear task and a clear Definition of Done.

For example: “Add export to CSV. Existing tests must pass. Add one new test. Do not change unrelated files.”

That gives the agent a clear target and gives you a simple way to review the result.

Skilled

Keep task instructions separate from run state.

The prompt should say what needs to happen. A file, database, or workflow system should track what already happened.

This matters on longer tasks. The agent should read current state instead of trying to remember everything from previous messages.

Expert

Move important controls out of prompts.

If a rule really matters, enforce it with code, permissions, or gates. Do not rely only on a Markdown instruction such as “do not deploy.”

Use the model for reasoning. Use the harness for control.

By the end, learners can explain the main parts of a harness and how a task moves from specification to verified completion.

01
Simple mental model

Model. Agent. Harness.

Model

Generates language, code, plans and reasoning.

Agent

Uses tools to complete work toward a goal.

Harness

Controls the work: rules, context, tools, checks, evidence and completion.

Think of these as three layers.

A model generates an answer. An agent gives that model a job, tools, and a loop. A harness controls how that agent works.

For example, the harness may decide which files the agent can edit, which tests must run, and whether another agent needs to review the result.

This distinction helps when debugging. Sometimes the model is not the problem. The workflow around it is.

Starter

Do not assume a stronger model will fix a weak process.

If results are poor, first check the task, context, and completion criteria.

A clearer workflow often improves results more than adding more prompt text.

Skilled

Give each agent one clear responsibility.

A planner should plan. A builder should build. A reviewer should review.

Clear roles make it easier to see where something failed and easier to improve one part without changing everything else.

Expert

Treat agents as replaceable workers.

Keep stable input and output contracts around them. Then you can swap models or change agent logic without rebuilding the whole workflow.

This is especially useful when model capabilities change quickly.

02
Why harnesses exist

Powerful agents still need operating rules.

Loose AI work

Broad prompts, unclear context, unknown tool use, hard-to-read failures and uncertain completion.

Harnessed AI work

Clear task, scoped tools, company rules, validation checks, evidence and a repeatable run record.

Without a harness, agent work can become hard to control.

The agent may get too much context. It may use the wrong tool. It may stop too early. It may say the work is done without proving it.

A harness adds structure. It limits what the agent can do. It records what happened. It checks the result before accepting it.

The goal is not to slow the agent down. The goal is to make useful autonomy safer and more predictable.

Starter

Do not hide important requirements inside paragraphs.

Turn them into a short checklist.

A checklist is easier for the agent to follow and easier for you to verify.

Skilled

Do not let the same agent write the work and be the only judge of the work.

Use tests, linters, schemas, CI, or a separate reviewer.

Independent checks catch mistakes that the working agent may miss.

Expert

Use clear end states.

A run should finish with something explicit such as PASS, FAIL, REFUSED, or NEEDS APPROVAL.

This makes automation easier because the next step does not depend on guessing what the agent meant.

03
The harness loop

From request to verified result.

1

Specify

Define goal, scope, constraints and Definition of Done.

2

Plan

Break work into steps and decide who or what should run.

3

Execute

Agents use approved tools to complete work.

4

Validate

Tests, reviews and gates decide whether work is accepted.

5

Observe and improve

Record what happened and reuse lessons for future runs.

A harness usually follows a simple loop.

First, define the work. Then plan it. Then let the agent act. After that, check the result. Finally, record what happened and use that information next time.

That last step matters.

A good harness does not just complete tasks. It gets better at completing similar tasks because failures, fixes, and useful patterns can be reused.

Starter

Write your specification so the AI can check it.

Avoid vague instructions like “make sure this works.”

Use checks such as: feature is implemented, required test was added, existing tests pass, and no unrelated files changed.

That makes “done” much easier to prove.

Skilled

Store run state outside the conversation.

Keep plans, approvals, test results, and changed files in structured storage.

This makes longer runs easier to resume and makes debugging much easier.

Expert

Treat the loop like a state machine.

Each step should have clear inputs, outputs, and allowed next steps.

This gives you better recovery, better replay, and much stronger control over complex agent workflows.

04
Core components

The parts of a harness.

Instructions

Project and company rules.

Context

Relevant information for this task.

Agents

Roles that perform work.

Skills

Reusable ways to do repeatable work.

Tools

Allowed ways to act.

Coordination

Who runs when.

Gates

Checks before acceptance.

Evidence

Records, outputs and proof.

Most harnesses use the same basic building blocks, even if they use different names.

Instructions define rules. Context gives the agent useful information. Agents do the work. Skills describe reusable ways to do work. Tools let agents act. Coordination decides what runs next. Gates check the result. Evidence records what happened.

Why care? Because separating these parts makes the system easier to understand and easier to improve.

Starter

If a rule matters more than once, put it somewhere reusable.

Do not keep repeating the same instruction in every prompt.

Move it into the spec, a shared rule, or a reusable skill.

Skilled

Keep components separate.

Do not let one agent own planning, execution, validation, and approval if those jobs can be split.

Clear boundaries make failures easier to diagnose.

Expert

Use structured formats when precision matters.

Schemas, enums, typed events, and validated configuration are easier to test than free-form text.

Use prose to explain. Use structure to control.

05
Agents, skills and tools

Three pieces people often mix up.

Agent

Who does the work. Example: planner, builder, reviewer.

Skill

How repeatable work is performed. Example: write a spec, review a PR.

Tool

What an agent can use. Example: read files, edit code, run tests.

An agent is the worker.

A skill is the reusable way that worker performs a task.

A tool is what the worker can use.

For example, a review agent may use a PR-review skill and tools that read diffs and run tests.

Keeping these separate matters because you can improve the skill without changing the tool, or change the model without redesigning the whole workflow.

Starter

Give each agent one clear job.

“Review this pull request for security issues” is better than “review everything and fix anything you find.”

Smaller roles are easier to test and easier to trust.

Skilled

Make tools return clear results.

Do not return an empty response and make the agent guess what happened.

Return status, errors, counts, and useful details.

Good tool design reduces bad reasoning.

Expert

Use typed tool interfaces for important operations.

Validate inputs and outputs before the agent can continue.

For high-risk actions, strongly typed runtime code can enforce timeouts, permissions, and error handling much more reliably than prompt instructions.

06
Spec + Definition of Done

The harness needs to know what “done” means.

Specification

Goal, scope, inputs, constraints, exclusions and expected output.

Definition of Done

Checks that must pass before the work is accepted.

Interactive question What could go wrong if an agent starts coding before the Definition of Done is clear?

The specification explains what should be built.

The Definition of Done explains what must be true before the work is accepted.

These are different.

For example, the spec may say, “Users can export a report as CSV.”

The Definition of Done may say: export works, permissions are checked, one test is added, existing tests pass, and no unrelated files changed.

This gives the agent a clear finish line.

Starter

Do not write a long prompt and hope the agent finds the important parts.

Use a short spec with clear sections and a clear Definition of Done.

This is one of the easiest ways to improve agent results.

Skilled

Make Definition of Done checks executable when you can.

If a test, schema, API response, or fixture can prove something, use that instead of asking the model whether it looks correct.

Expert

Turn important Definition of Done checks into gates.

A gate should inspect evidence and return a result.

The agent can propose that work is complete. The gate should decide whether it actually passed.

07
Company alignment

Harnesses help agents follow company rules.

Examples of rules

  • No production secrets.
  • No unscoped file changes.
  • Tests required for code changes.
  • Human approval for deployment.
  • Record tool calls and evidence.

Why it matters

Team standards should live in the workflow, not only in someone’s memory.

A harness can help turn company standards into part of the workflow.

For example, a company may require tests for code changes, block access to production secrets, or require human approval before deployment.

These rules are stronger when the harness enforces them.

A prompt can say “do not deploy.” A harness can make the deploy tool unavailable until approval exists.

That is the difference between asking and enforcing.

Starter

Put repeated company rules into the workflow.

If everyone has to remember the same instruction every time, it probably belongs in the harness.

This reduces mistakes and saves time.

Skilled

Prefer enforcement over reminders.

Use protected branches, tool permissions, sandboxing, approval checks, and CI when possible.

The more important the rule, the less you should depend on the model remembering it.

Expert

Do not rely on Markdown files for critical safety rules.

Files such as CLAUDE.md or AGENTS.md are useful for guidance.

Hard boundaries should live in permissions, runtime policy, and gates that the agent cannot simply ignore.

Take a simple request: “Add report export.”

A harness turns that into a controlled sequence.

First, create a spec and Definition of Done. Then identify the files and risks. Give the builder the tools it needs. Run the work. Run tests and reviews. Record the evidence. Accept the result only when the required checks pass.

If a test fails, the harness should record the failure and decide whether to repair, replan, or stop.

Starter

Start with small tasks.

A narrow task with one clear outcome is easier to review and easier to debug.

If something goes wrong, you can usually tell whether the problem came from the spec, the agent, or the implementation.

Skilled

Validate against the real source of truth.

If the answer exists in a database, test runner, API, log, or source file, read it directly.

Do not ask the model to remember whether something passed.

Expert

Create a receipt for each run.

Record what the agent received, what tools it used, what changed, what checks ran, and why the run passed or failed.

Receipts make complex agent systems much easier to audit and replay.

09
Close

The harness is the workplace, rulebook and inspection station for AI agents.

What learners should remember

  • A harness is more than a prompt.
  • Specifications define work.
  • Definition of Done defines acceptance.
  • Tools and permissions control action.
  • Gates and evidence create trust.

Next step

Use a team-specific harness walkthrough to show where these concepts appear in the actual internal workflow.

Harnesses get better as more important behaviour moves out of prompts and into the system around the model.

Start with clear specs and checks.

Then add reusable skills, better tools, stored state, independent validation, and stronger controls.

The goal is not to remove AI reasoning.

The goal is to make sure important decisions can be checked and trusted.

Starter

Start simple.

Use a clear spec, a clear Definition of Done, limited tools, and visible checks.

That already gives you a useful harness pattern.

Skilled

When you see the same workflow more than once, make it reusable.

Turn repeated instructions into skills. Store state outside the chat. Add independent validation.

That reduces repeated work and improves consistency.

Expert

Use deterministic systems around probabilistic models.

Typed state, gates, receipts, replay, and runtime policy give you reliable control while still letting the model handle reasoning and planning.

That balance is where advanced harness design becomes powerful.
